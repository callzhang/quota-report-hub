# Quota Report Hub 中文运行说明

## 团队 Token 用量统计

Hub 提供独立的 `token-usage.html` 页面。登录后默认查询最近 7 天，按小时、Hub 用户分组并显示 Total；可按时间、Hub 用户、提供方、模型账户、原始模型名筛选，也可切换聚合颗粒度、分组和指标。每个 Hub 用户的汇总直接放在 Breakdown，不再重复设置右侧面板。页面只读取 `GET /api/token-usage-query`，同一登录会话中完全相同的查询缓存 5 分钟。

每次 15 分钟 quota guard 运行时同时执行用量采集，单轮最多使用 10 秒。每台机器首次运行固定回扫最近 72 小时；之后只从已确认的文件位置向后读取新增或更新内容。Codex 按累计 `token_count` 计算正向增量并去除复制历史，Claude 按最终 assistant message ID 更新计数。quota guard 自动切换时按写凭证前记录的精确时间切分；用户手动切换时按汇报当时观察到的账户归属，因此允许一个汇报周期内的小误差。

Total 保持提供方原始定义；Input、Output 是组成部分，Cache Read、Cache Write 和 Codex Reasoning 是 Total 的子集，不能再次相加。Claude Total 按原始记录包含 input、output、cache read 和 cache creation/write。模型名不使用固定白名单，新出现的 GPT 或 Claude 模型会原样统计和展示。

隐私边界：上传内容仅包含 15 分钟数字汇总——Hub 用户由登录身份确定，另含提供方、模型账户、原始模型、时间桶和 6 个计数。不会上传 prompt、response、项目名、对话标题、工具内容、本地路径、session/message ID、记录指纹或文件位置。本地状态位于 `~/.agents/auth/token-usage.sqlite3`，权限仅限当前用户。待上传批次可幂等重试；服务端明确拒绝的无效批次只推进一次，不会无限重报。

`POST /api/token-usage` 接收有上限且幂等的批次；`GET /api/token-usage-query` 返回总计、受限趋势点、四维明细和每个 Hub 用户的上报状态。15 分钟明细保留并可查询 90 天；受保护的每日 `/api/cron/token-usage-retention` 每次最多把 7 个旧 UTC 日期压缩为日汇总，同时清理旧回执。账户首页、revision 轮询、quota 写入/历史与 fetch-best 都不会读取 token 用量表。

Vercel Functions 固定运行在 `pdx1`，与 Turso 数据库的 AWS `us-west-2` 位置一致。数据库请求不再跨美国东西海岸，静态页面仍由 Vercel CDN 就近提供。

Token 用量只读请求不会在 Serverless 冷启动时执行建表或迁移；认证查询与 `last_used_at` 更新合并为一个数据库批次，随后只执行一个有界统计批次。

设计基准为 95 个文件、约 2.9 GB 历史：完整解析约 44.97 秒，峰值内存约 54 MB。正常定时运行从字节位置增量读取，并受 10 秒预算限制，因此开销远低于完整回扫。

项目安装、部署和完整 API 说明见 [README.md](README.md)。本页重点解释 Hub 页面如何判断账号状态，以及如何排查“Probe 正常但 Quota 不可用”。

## 账号生命周期与单一主状态

页面每个账号只显示一个主状态，回答的是“共享池现在能不能使用这个账号”：

| 主状态 | 含义 |
|---|---|
| `AVAILABLE` | 当前额度证据完整、在有效期内，并且达到轮换门槛。Codex 要求周额度至少 5%；Claude 同时要求 5 小时额度至少 20%、周额度至少 5%。 |
| `LOW QUOTA` | 当前额度证据完整，但至少一个额度低于门槛；账号不会作为当前可用候选。 |
| `WAITING FOR NEW QUOTA` | 上一个额度周期已经重置，但重置后尚未收到新快照。旧值只是历史记录。 |
| `QUOTA UNKNOWN` | 当前额度证据缺失、过旧、不完整，或者来自失败的探测；不能据此判断账号当前可用。 |
| `UNAVAILABLE` | 凭证被拒绝或失效、访问令牌过期且不能恢复，或者账号不符合共享条件，需要处理登录或账号资格。 |

状态优先按凭证不可用、等待新周期、额度未知、低额度、可用来判断。这样即使存在旧的高额度记录，失效凭证也不会被显示为可用。

## Probe、Token、Quota、Refresh 的关系

它们是同一生命周期中的不同证据，不是四个并列结论：

1. `Token uploaded` 表示凭证何时进入 Hub；它不证明凭证现在仍有效。
2. `Refresh` 表示刷新令牌是否被实际验证。`verified` 是验证通过，`rejected` 是服务端明确拒绝，`not tested` 只表示没有完成验证，不等于失败。
3. `Probe` 表示最近一次联系供应商是否成功。Probe `ok` 只证明那次请求成功，不保证响应包含完整、仍在有效期内的额度窗口。
4. `Quota` 是由探测或本地上报得到的额度证据。只有所需窗口齐全、报告不超过一小时、且窗口的重置时间仍在未来，额度才是“当前额度”。
5. Hub 综合上述证据生成唯一的主状态；共享池按主状态和额度门槛决定是否可用。

因此 Probe `ok` 但 Quota 不可用并不矛盾。例如，探测请求成功，但 Claude 只返回了周额度、没有 5 小时额度，主状态就是 `QUOTA UNKNOWN`；如果最后一个额度窗口已经重置而新数据尚未来，则是 `WAITING FOR NEW QUOTA`。

## 额度时间与历史记录

鼠标悬停、键盘聚焦或触摸主状态可以打开详情；按 Escape、关闭按钮或点击外部关闭。详情同步显示最新快照和诊断信息，并按需加载过去 24 小时的额度图。

- `Captured` 是这一条具体额度窗口实际被观察到的时间。不同窗口可能来自不同时间，不能用整行最近上报时间替代。
- `Reset` 是供应商给出的该额度窗口重置边界，不是采集时间。
- 灰色并标有 `Historical - not current quota` 的值仅用于回看，不能作为当前可用额度。
- 图中的缺失或失败读数显示为断点，不进行插值；跨越重置边界时也会断开，避免把两个额度周期连成一条误导性的趋势线。
- `/api/quota-history` 每次只查询精确的 `source + account_id`，最多返回过去 24 小时的 96 个点，不包含任何认证材料。

## 自动刷新与数据库读取

首次登录时，浏览器读取一次完整 `/api/status`。之后可见页面每分钟以及重新回到前台时，只读取单行 `dashboard_revision`。仅当 revision 变化时，才重新读取完整状态；隐藏页面不轮询，同一时刻的重复请求会合并。

完整状态响应会签发一个有效期 12 小时、只允许访问 `/api/status-revision` 的 `qrr.` 票据。它采用无数据库会话验证，因此常规检查不会读取或更新个人 API token 行。代价是该票据在有效期内不能像个人 `qrp.` token 那样通过数据库立即撤销；它只能读取 revision 数字，不能读取账号、额度或凭证，所以权限被限制在最低范围。完整状态和历史接口仍必须使用可撤销的个人 token。

额度历史不随完整状态一起读取。只有打开某个账号详情时才查询，并在当前浏览器登录会话中缓存 5 分钟；同一账号的并发打开复用同一个请求。这样日常自动刷新不会扫描额度事件历史。

## 排查顺序

当看到 Probe `ok` 但额度不可用时：

1. 先看主状态，不要把 Probe `ok` 当作账号 `AVAILABLE`。
2. 打开详情，比较 Probe 时间、各窗口的 `Captured` 和 `Reset`。
3. 若是 `WAITING FOR NEW QUOTA`，等待重置后的新上报；旧额度不会自动变成 100%。
4. 若是 `QUOTA UNKNOWN`，检查是否缺少所需窗口、报告是否超过一小时，或最近探测是否只返回了部分额度。
5. 只有 `UNAVAILABLE` 且详情显示凭证被拒绝或失效时，才要求账号所有者重新登录。

浏览器网络或服务临时错误会保留最后一次页面数据并自动重试。只有本地没有 token，或服务端明确返回 `401` 时，页面才显示登录界面；已经有效登录时不需要再次点击登录。
